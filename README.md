## Цель работы

Исследование стратегий потоковой агрегации метрик и реализация на Go прототипа
распределённой системы сбора метрик с подключаемыми стратегиями агрегации для их
сравнения по точности, задержке и потреблению ресурсов в идентичных условиях.

## Задачи

1. Изучить существующие системы мониторинга (Prometheus, VictoriaMetrics,
   OpenTelemetry Collector, StatsD, M3) и используемые в них способы агрегации.
2. Классифицировать стратегии потоковой агрегации (фиксированные и скользящие окна,
   иерархическая предагрегация, вероятностные структуры данных) с точки зрения
   объединяемости агрегатов, оценок точности и затрат памяти.
3. Спроектировать архитектуру распределённой системы: агенты, брокер сообщений,
   узлы агрегации, хранилище.
4. Реализовать на Go прототип, в котором стратегии подключаются через единый
   интерфейс и заменяются без доработки остальных компонентов.
5. Разработать испытательную среду и генератор метрик с настраиваемыми
   интенсивностью потока, кардинальностью и всплесками.
6. Сравнить стратегии по пропускной способности, задержке, потреблению памяти и
   погрешности; выработать рекомендации по выбору стратегии.

## Гипотезы

- Предагрегация на агенте снижает сетевой трафик и нагрузку на узлы агрегации
  без потери точности для объединяемых агрегатов (сумма, количество, минимум,
  максимум) при условии отсутствия дублей при доставке.
- Скетчи квантилей позволяют оценивать p95/p99 при фиксированном объёме памяти;
  сравниваются скетчи с доказанными гарантиями погрешности и без них.
- Скользящие окна уменьшают задержку обнаружения изменений по сравнению
  с фиксированными ценой роста потребления памяти и CPU.

Точка отсчёта (эталон): передача и хранение сырых точек без агрегации,
по которым вычисляются точные значения.

## Архитектура (планируемая)

```
┌────────────┐      ┌───────────────┐      ┌─────────────────┐      ┌────────────┐
│   Агенты   │─────►│     Kafka     │─────►│ Узлы агрегации  │─────►│ ClickHouse │
│(предагрег.)│      │ партиция =    │      │ (consumer group,│      │ (агрегаты  │
└────────────┘      │ hash(ряда)    │      │  стратегии)     │      │ и эталон)  │
      ▲             └───────────────┘      └─────────────────┘      └────────────┘
      │
┌────────────┐
│ Генератор  │
│  нагрузки  │
└────────────┘
```

Партиционирование по ключу временного ряда гарантирует, что все точки одного ряда
обрабатываются одним узлом агрегации, что необходимо для корректной агрегации.

## Стратегии агрегации

| Стратегия | Статус |
|---|---|
| Эталон: сырые точки без агрегации | запланировано |
| Фиксированные окна (tumbling) | в работе |
| Скользящие окна (sliding) | запланировано |
| Иерархическая предагрегация на агенте | запланировано |
| Скетчи квантилей: t-digest, DDSketch | запланировано |

Все стратегии реализуют общий интерфейс `Aggregator`
(`internal/strategy/strategy.go`). Частичные агрегаты объединяются методом
`Merge`, что позволяет строить иерархическую агрегацию.

## Стек технологий

- Go 1.26+ (горутины, каналы, `context`, `sync`)
- Apache Kafka — буферизация и партиционирование потока
- ClickHouse — хранение агрегатов и эталонных данных
- Docker Compose — испытательный стенд с ограничением ресурсов
- Prometheus и Grafana — мониторинг самого стенда
- `go test`, бенчмарки, `pprof` — тестирование и профилирование

## Структура проекта

```
cmd/
  agent/        агент сбора и предагрегации метрик
  aggregator/   узел агрегации
  generator/    генератор нагрузки
internal/
  model/        базовые типы: точка, метки, ключ ряда
  strategy/     интерфейс Aggregator и стратегии агрегации
docs/           документация и материалы работы
```

go vet ./...           # статический анализ
